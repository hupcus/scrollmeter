# Measurement decisions (ADR log)

One entry per non-obvious Android or measurement decision (spec §72). Newest at the bottom; never delete,
supersede with a new entry that references the old one.

| ADR-001 | 2026-09-23 | The metric is **scroll distance** (content displacement, fling included, direction changes add up), not the finger's path. | Raw `MotionEvent`s are not available across apps on a stock device; scroll deltas are. Spec §1, §7, §12. | accepted |
| ADR-002 | 2026-09-23 | `minSdk = 28`. | `AccessibilityRecord.getScrollDeltaX/Y()` exist from API 28 and are the primary source. | accepted |

| ADR-004 | 2026-09-23 | Toolchain pinned to JDK 21 / Gradle 8.14.3 / AGP 8.13.2 / Kotlin 2.3.21 / Compose BOM 2026.06.01. | Same pins build on this Mac in DETECT (08/2026); AGP 8 does not support JDK 25; AGP 9 breaks the KSP/Room set-up. | accepted |
| ADR-005 | 2026-09-23 | All tunables in `measurement/MeasurementConfig.kt` (outlier factor 4×, fallback gap 2 s, dedupe window 5 ms, flush 10 s / 50 events, session gap 60 s, card 85.60 mm). | Spec §11, §16, §18, §70: one place to retune after real data. | accepted |
| ADR-006 | 2026-09-23 | Duplicate suppression is **off** by default; enabling requires evidence from debug CSVs (same package + windowId + dx + dy within ≤ 5 ms). | Over-eager dedupe under-measures; spec §70. | accepted |
| ADR-007 | 2026-09-23 | Historical `distanceMm` is never recomputed after recalibration; aggregates carry `calibrationVersion`. | Stable history, no raw event retention. Spec §65. | accepted |
| ADR-008 | 2026-09-23 | App labels via `PackageManager` with a `<queries>` element for the launcher intent (`MAIN`/`LAUNCHER`); no `QUERY_ALL_PACKAGES`. | Package visibility on API 30+; the launcher-intent query is Play-compliant and covers the apps people scroll in. Missing label → show the package name. | accepted |
| ADR-009 | 2026-09-23 | No foreground service, no WorkManager for capture. | The accessibility service is system-managed; spec §40, §41. | accepted |
| ADR-010 | 2026-09-23 | Debug screen, test-list screen and raw event logging live in `src/debug/` only. | Never ship raw event handling; spec §34, §66. | accepted |
| ADR-011 | 2026-09-23 | Sessions are persisted (one row per closed session) but have no UI in the MVP. | Cheap to store, enables Phase 1.1 features without re-collecting; spec §18. | accepted |
| ADR-012 | 2026-09-23 | Charts are a custom Compose `Canvas` bar chart; no chart library. | Spec §23; no dependency, no network. | accepted |
| ADR-013 | 2026-09-23 | `canRetrieveWindowContent` stays `false`. | Measured on the test phone: Chrome 153.0.8010.52 delivers `TYPE_VIEW_SCROLLED` without it — direct deltas from a `FrameLayout` plus positions from the `WebView` node (see ADR-020), 0.00 % against its own position stream. The Facebook in-app browser also reports direct deltas. YouTube stays silent after a cold start — and still does with `true` (throwaway branch `throwaway/can-retrieve-window-content`, local only), so the flag would buy nothing there. | accepted (evidence) |
| ADR-014 | 2026-09-23 | A scroll event whose `scrollDeltaX` **and** `scrollDeltaY` are both `-1` carries no delta and goes to the position fallback, like (0, 0). A single `-1` on one axis is a real 1 px scroll. | `AccessibilityRecord` initialises both deltas to `UNDEFINED = -1` (android-36 sources, pinned by `AccessibilityEventParserTest`); only `View` and frameworks that call `setScrollDeltaX/Y` overwrite it. Treating (-1, -1) as a 1.4 px scroll would hide every app that sends positions only. | accepted |
| ADR-015 | 2026-09-23 | Fallback tracker: key = package + windowId + className + the axes the scrollable reports (`maxScrollX > 0`, `maxScrollY > 0`); a position is valid when `scrollX/Y ≥ 0` and not above a positive `maxScrollX/Y`; an invalid position forgets the key; a zero position change is UNMEASURABLE; a jump above the outlier limit is UNMEASURABLE (not OUTLIER); at most 64 keys (LRU). | Spec §6 B — every doubt resolves to "no fallback" rather than a guessed distance. Constants in `MeasurementConfig`. The axes joined the key after the test phone showed `windowId = -1` on **every** event without `canRetrieveWindowContent`: a horizontal carousel and a vertical list of one app would otherwise be diffed against each other. | accepted |
| ADR-016 | 2026-09-23 | Physical scale in Phase 1: `xdpi`/`ydpi` (DISPLAY_METRICS, MEDIUM); a dpi outside 100–1000 counts as broken — one broken axis is replaced by the other (LOW); both broken → `densityDpi` as method UNKNOWN, confidence LOW. | Spec §9 and §33 (`UNKNOWN → LOW`); `densityDpi` stays a last resort, never the primary conversion (spec §56). Phase 2 puts the manual card calibration on top. | accepted |
| ADR-017 | 2026-09-23 | Debug builds keep the newest 100 events on screen and up to 20 000 in RAM for one CSV export (per-app run); our own EXCLUDED events are not logged (scrolling the debug list would flood it). Every logged event is also written through to app-private `files/debug/recording.csv` (package, class, numbers — the export's columns) until Clear; Export writes that whole file, and `adb exec-out run-as <app> cat files/debug/recording.csv` reads it without Export. None of it exists in release. | Spec §34 asks for ~100 on screen; a 20–30 s manual run per app produces a few hundred to ~2 000 events, which a 100-event buffer would lose. **Amended 2026-09-23:** the first manual run was lost because ColorOS's memory guard (`OsenseKillAction`, `o-kill(4010)`, free RAM < 2 GB) killed the service's process three times in 45 s while heavy apps ran; the system restarted the service after 4–10 s each time, but a RAM-only log does not survive that. | accepted |
| ADR-018 | 2026-09-23 | The accessibility service is declared `android:exported="false"` with `BIND_ACCESSIBILITY_SERVICE`. | Only the system binds it; no other app has a reason to reach it. Verified on the test phone in Phase 1 (the system binds and delivers events). | accepted |
| ADR-019 | 2026-09-23 | A Compose **lazy** list (`LazyColumn`/`LazyRow`) is UNMEASURABLE. The tracker recognises its position as an estimate — `maxScroll − scroll == 100` (`COMPOSE_LAZY_MAX_SCROLL_MARGIN_PX`) on a key seen for the first time or whose `maxScroll` moved since its previous event (an exact scrollable keeps its max, so passing 100 px before its end marks nothing) — and marks the key for as long as it lives, so the end of the list (where `max == scroll`) is not trusted either. Compose `verticalScroll`/`horizontalScroll` keep exact positions and are measured through the fallback. | Compose foundation 1.11.4 sends scroll events without deltas and reports `firstVisibleItemScrollOffset + firstVisibleItemIndex × 500` with `max = that + 100` (`LazyLayoutSemantics`, verified with `javap`). Measured on our test list: +110 to +115 % against ground truth before the rule, 0 counted after it. Spec §6 C, §72: an index is not a distance. Apps built on lazy Compose lists will read as *limited* until a better source exists. | accepted |
| ADR-020 | 2026-09-23 | A valid position fallback is **not counted** (`SUPERSEDED_BY_DIRECT`, kept in the debug CSV) when a *different view class* of the same package delivered a direct delta within the last 5 s (`DIRECT_SUPERSEDES_FALLBACK_MS`). Within one class, mixing stays allowed — the tracker already diffs against the direct event's position. | Chrome reports every scroll twice: deltas from a `FrameLayout` and positions from the `WebView` node; the WebView position always ended within 1–15 px of the cumulative FrameLayout delta. Counting both measured 1558 px for an 808 px scroll (~2×). The §70 duplicate rule (same dx/dy within 5 ms) cannot see it — the two streams differ in shape and timing. Cost: an app scrolling a delta-reporting view and a position-only view *at the same time* under-counts the latter; judged far less harmful than a 2× over-count. | accepted |
| ADR-021 | 2026-09-23 | **Time in app** (requested by Honza: the dashboard shows time *and* metres per app). Source: `UsageStatsManager.queryEvents` — ACTIVITY_RESUMED / PAUSED / STOPPED (ints 1 / 2 = MOVE_TO_FOREGROUND / BACKGROUND on API 28), SCREEN_NON_INTERACTIVE and DEVICE_SHUTDOWN as closers — aggregated by our pure-Kotlin `ForegroundTimeAggregator` per local day and package into `daily_app_usage` (replace on sync). `PACKAGE_USAGE_STATS` is declared (`tools:ignore="ProtectedPermissions"`) and **optional**: granted in Usage-access settings after an in-app disclosure; every distance feature works without it, and an unknown value shows as "—", never 0. Sync on app open and from the service at day change / stale connect; no WorkManager (ADR-009 stands). Accessibility stays `typeViewScrolled` only — `TYPE_WINDOW_STATE_CHANGED` rejected. Export adds `foreground_ms` / `active_scroll_ms` (deviation from SPEC §28). | The OS keeps usage events only ~10 days (AOSP `UsageStatsDatabase.prune`), so a daily snapshot is required; the system's daily buckets are UTC days (`UnixCalendar`), so local days need event-level aggregation. Google Play lists no declaration form for this permission (Permissions & APIs policy, answer 9888170 / 16558241; Declaration Form 9214102); the User Data policy treats app usage as sensitive → prominent disclosure; data processed only on the device needs no Data-safety entry (10787469). Widening accessibility events would void the "scroll events only" policy, disclosure and guard tests. Package names come back without `QUERY_ALL_PACKAGES` (AOSP `UsageStatsService`). | accepted (scope); details revisited in Phase 3 |
| ADR-022 | 2026-09-23 | **Active scroll time** `activeScrollMs` per (date, package): Σ of gaps ≤ `ACTIVE_SCROLL_GAP_MS = 5_000` between consecutive counted events of the same package, accumulated in `ScrollAccumulator`; 60 s sessions unchanged. Pace (m/min) = distance / time in app when Usage access is granted, distance / active scroll time otherwise — always labelled which. | SPEC §50 (`distanceMm / activeScrollDuration`, ordinary pauses excluded); needs no permission, so the dashboard always has a time dimension; the constant is tunable in `MeasurementConfig`. | accepted |
