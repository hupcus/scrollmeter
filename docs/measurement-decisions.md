| ADR-013 | 2026-09-23 | `canRetrieveWindowContent` stays `false`. | Measured on the test phone: Chrome 153.0.8010.52 delivers `TYPE_VIEW_SCROLLED` without it — direct deltas from a `FrameLayout` plus positions from the `WebView` node (see ADR-020), 0.00 % against its own position stream. | ADR-014 | 2026-09-23 | A scroll event whose `scrollDeltaX` **and** `scrollDeltaY` are both `-1` carries no delta and goes to the position fallback, like (0, 0). A single `-1` on one axis is a real 1 px scroll. | `AccessibilityRecord` initialises both deltas to `UNDEFINED = -1` (android-36 sources, pinned by `AccessibilityEventParserTest`); only `View` and frameworks that call `setScrollDeltaX/Y` overwrite it. Treating (-1, -1) as a 1.4 px scroll would hide every app that sends positions only. | accepted |
| ADR-015 | 2026-09-23 | Fallback tracker: key = package + windowId + className + the axes the scrollable reports (`maxScrollX > 0`, `maxScrollY > 0`); a position is valid when `scrollX/Y ≥ 0` and not above a positive `maxScrollX/Y`; an invalid position forgets the key; a zero position change is UNMEASURABLE; a jump above the outlier limit is UNMEASURABLE (not OUTLIER); at most 64 keys (LRU). | Spec §6 B — every doubt resolves to "no fallback" rather than a guessed distance. Constants in `MeasurementConfig`. The axes joined the key after the test phone showed `windowId = -1` on **every** event without `canRetrieveWindowContent`: a horizontal carousel and a vertical list of one app would otherwise be diffed against each other. | accepted |
| ADR-016 | 2026-09-23 | Physical scale in Phase 1: `xdpi`/`ydpi` (DISPLAY_METRICS, MEDIUM); a dpi outside 100–1000 counts as broken — one broken axis is replaced by the other (LOW); both broken → `densityDpi` as method UNKNOWN, confidence LOW. | Spec §9 and §33 (`UNKNOWN → LOW`); `densityDpi` stays a last resort, never the primary conversion (spec §56). Phase 2 puts the manual card calibration on top. | accepted |
| ADR-017 | 2026-09-23 | Debug builds keep the newest 100 events on screen and up to 20 000 in RAM for one CSV export (per-app run); our own EXCLUDED events are not logged (scrolling the debug list would flood it). | ADR-018 | 2026-09-23 | The accessibility service is declared `android:exported="false"` with `BIND_ACCESSIBILITY_SERVICE`. | Only the system binds it; no other app has a reason to reach it. Verified on the test phone in Phase 1 (the system binds and delivers events). | accepted |
| ADR-019 | 2026-09-23 | A Compose **lazy** list (`LazyColumn`/`LazyRow`) is UNMEASURABLE. The tracker recognises its position as an estimate — `maxScroll − scroll == 100` (`COMPOSE_LAZY_MAX_SCROLL_MARGIN_PX`) on a key seen for the first time or whose `maxScroll` moved since its previous event (an exact scrollable keeps its max, so passing 100 px before its end marks nothing) — and marks the key for as long as it lives, so the end of the list (where `max == scroll`) is not trusted either. Compose `verticalScroll`/`horizontalScroll` keep exact positions and are measured through the fallback. | Compose foundation 1.11.4 sends scroll events without deltas and reports `firstVisibleItemScrollOffset + firstVisibleItemIndex × 500` with `max = that + 100` (`LazyLayoutSemantics`, verified with `javap`). Measured on our test list: +110 to +115 % against ground truth before the rule, 0 counted after it. Spec §6 C, §72: an index is not a distance. Apps built on lazy Compose lists will read as *limited* until a better source exists. | accepted |
| ADR-020 | 2026-09-23 | A valid position fallback is **not counted** (`SUPERSEDED_BY_DIRECT`, kept in the debug CSV) when a *different view class* of the same package delivered a direct delta within the last 5 s (`DIRECT_SUPERSEDES_FALLBACK_MS`). Within one class, mixing stays allowed — the tracker already diffs against the direct event's position. | Chrome reports every scroll twice: deltas from a `FrameLayout` and positions from the `WebView` node; the WebView position always ended within 1–15 px of the cumulative FrameLayout delta. Counting both measured 1558 px for an 808 px scroll (~2×). The §70 duplicate rule (same dx/dy within 5 ms) cannot see it — the two streams differ in shape and timing. Cost: an app scrolling a delta-reporting view and a position-only view *at the same time* under-counts the latter; judged far less harmful than a 2× over-count. | accepted |
| ADR-021 | 2026-09-23 | **Time in app** (requested by Honza: the dashboard shows time *and* metres per app). Source: `UsageStatsManager.queryEvents` — ACTIVITY_RESUMED / PAUSED / STOPPED (ints 1 / 2 = MOVE_TO_FOREGROUND / BACKGROUND on API 28), SCREEN_NON_INTERACTIVE and DEVICE_SHUTDOWN as closers — aggregated by our pure-Kotlin `ForegroundTimeAggregator` per local day and package into `daily_app_usage` (replace on sync). `PACKAGE_USAGE_STATS` is declared (`tools:ignore="ProtectedPermissions"`) and **optional**: granted in Usage-access settings after an in-app disclosure; every distance feature works without it, and an unknown value shows as "—", never 0. Sync on app open and from the service at day change / stale connect; no WorkManager (ADR-009 stands). Accessibility stays `typeViewScrolled` only — `TYPE_WINDOW_STATE_CHANGED` rejected. Export adds `foreground_ms` / `active_scroll_ms` (deviation from SPEC §28). | The OS keeps usage events only ~10 days (AOSP `UsageStatsDatabase.prune`), so a daily snapshot is required; the system's daily buckets are UTC days (`UnixCalendar`), so local days need event-level aggregation. Google Play lists no declaration form for this permission (Permissions & APIs policy, answer 9888170 / 16558241; Declaration Form 9214102); the User Data policy treats app usage as sensitive → prominent disclosure; data processed only on the device needs no Data-safety entry (10787469). Widening accessibility events would void the "scroll events only" policy, disclosure and guard tests. Package names come back without `QUERY_ALL_PACKAGES` (AOSP `UsageStatsService`). | accepted (scope); details revisited in Phase 3 |
| ADR-022 | 2026-09-23 | **Active scroll time** `activeScrollMs` per (date, package): Σ of gaps ≤ `ACTIVE_SCROLL_GAP_MS = 5_000` between consecutive counted events of the same package, accumulated in `ScrollAccumulator`; 60 s sessions unchanged. Pace (m/min) = distance / time in app when Usage access is granted, distance / active scroll time otherwise — always labelled which. | SPEC §50 (`distanceMm / activeScrollDuration`, ordinary pauses excluded); needs no permission, so the dashboard always has a time dimension; the constant is tunable in `MeasurementConfig`. | accepted |
| ADR-023 | 2026-09-24 | Manual card calibration (Phase 2) uses a **vertical** bar — a deviation from SPEC §8's "vodorovný kalibrační pruh". The bar is drawn on a Compose `Canvas` in layout pixels, which are raw display pixels, and the saved `referencePx` is exactly the drawn length; `mmPerPxX = mmPerPxY = 85.60 / referencePx` (square pixels, spec §8). Slider range = `CardCalibration.plausibleReferencePx` (338–3370 px, i.e. the 100–1000 dpi range of ADR-016) ∩ the height free on screen, with −/+ buttons for 1 px steps. Start: the saved card length when it applies to this display, else the length xdpi/ydpi predict — the **mean** of both axes (PLAN said `85.6 / mmPerPxX` for a horizontal bar). | The card's long edge (85.60 mm) is wider than a phone held upright: the test phone is 1080 px ≈ 68 mm wide, the card needs ≈ 1360 px. Along the height (2400 px ≈ 151 mm) it fits with room for the controls; landscape would leave ≈ 54 mm of height for the card, the text and the controls. Pixels are square, so the axis the bar lies on does not change the result, and a vertical bar in portrait measures along Y — the axis almost all scrolling happens on. | accepted |
| ADR-024 | 2026-09-24 | **Calibration storage and applicability.** DataStore Preferences file `calibration` (app-private; `allowBackup=false`) holds method, `referencePx`, `mmPerPxX/Y`, `calibratedAt`, manufacturer, model, xdpi/ydpi at calibration, the panel's short × long edge in px, and `calibrationVersion`. The version counts the user's changes — a saved card, or "Přeskočit – použít automatický odhad" while a card was stored; 0 = never touched. A stored card **applies only** when manufacturer + model + panel size (short × long px, so rotation does not matter) equal the current default display; otherwise the scale is DISPLAY_METRICS under the stored version and the accuracy screen says why. xdpi is **not** part of that check. Incomplete or implausible stored values read as "no card"; a storage error reads as version 0 / no card (spec §61). The service converts nothing before the stored calibration is loaded (samples wait in the channel) and follows changes live; each `MeasurementResult` carries the version its distance was computed under and nothing is recomputed (spec §65, ADR-007). `DisplayMetricsProvider` keeps `Display.getRealMetrics` rather than `WindowMetrics` (PLAN's wording). | Pixels of one panel are not pixels of another: after a resolution switch (FHD+/QHD+ on phones that offer it) or a DataStore carried to another phone by a device-to-device transfer (open point in `handoff.md`), a stale card would apply a wrong scale with HIGH confidence — ~33 % off for 1440 → 1080 px. A card stays right when an OS update changes what xdpi reports, so xdpi does not invalidate it. `getRealMetrics` is the one call that gives the real size plus xdpi/ydpi from the non-visual service context on API 28–36; measured correct on the test phone in Phase 1 (1080×2400, 403.411 / 401.052). | accepted |
| ADR-025 | 2026-09-24 | **Time in app — the details left open by ADR-021.** (1) An app is in the foreground while ≥ 1 of its activities is RESUMED; the activity class is read **only** to pair RESUMED with PAUSED/STOPPED and is never stored. (2) When its last activity pauses it has *left* at that moment unless it resumes within `USAGE_SAME_APP_GRACE_MS = 2_000` and no other app came up meanwhile — another app's RESUMED ends it at its pause. (3) SCREEN_NON_INTERACTIVE and DEVICE_SHUTDOWN end every app; DEVICE_STARTUP without a shutdown before it discards what was still open (its end is unknown); an unpaired PAUSED is ignored; what is open at the end of the window ends at *now*. (4) Split screen counts both apps. (5) Intervals are split at **local** midnight (DST days have 23/25 h); a launch counts on the day of its RESUMED. (6) Window: whole local days from `max(lastSync − 1 day, now − USAGE_SYNC_MAX_DAYS = 9 days)`, events read from `USAGE_SYNC_LOOKBACK_MS = 12 h` before it; those days are replaced in one transaction. (7) The own package and the user's excluded apps are left out. (8) DataStore keeps the wall time of the last successful sync (`usage_sync_last_ms`) — PLAN called it `usageSyncLastEventTs`; the sync time is what the window needs. The service syncs on connect when that is ≥ `USAGE_SYNC_STALE_MS = 6 h` old (or in the future — a clock set back) and at every local day change; `MainActivity.onResume` always syncs. | Moving between two activities of one app pauses one before resuming the next (tens of ms apart); without the grace every such move would count as a new launch. The lead-in pairs an app that was already open at the first recomputed midnight. Measured on the API 34 emulator: after the first sync the per-app totals equal the system's own `totalTimeUsed` (`dumpsys usagestats`, today): launcher 13:34.4 vs 13:34, Settings 3:19.7 vs 3:20. Digital Wellbeing on a real phone is still on the verification debt list. | accepted |
| ADR-026 | 2026-09-24 | **Persistence (Phase 3).** Room v1 (`scrollmeter.db`, schema JSON in `app/schemas/`): `daily_app_aggregate` (SPEC §17 + `calibrationVersion` + `activeScrollMs`), `scroll_session`, `daily_app_usage`. A flush is one transaction of *insert-or-add* per (date, package): `INSERT OR IGNORE` of an empty row, then `UPDATE … SET x = x + :x`, first timestamp = MIN, last = MAX, `calibrationVersion` = MAX — two statements because API 28 ships SQLite 3.22 and `ON CONFLICT DO UPDATE` needs 3.24. The service's pipeline (`ScrollPipeline`, pure Kotlin, one thread via `Dispatchers.Default.limitedParallelism(1)`) writes every 10 s while data is pending, at the 50th event, at a new local day, on `onInterrupt`, and as the last act of the pipeline on unbind / destroy / reconnect; the write itself runs `NonCancellable` so a committed transaction is never restored and written twice; a failed write keeps its deltas and sessions for the next flush. Our own package is **never stored** — in debug test mode it is measured for the live comparison only. Debug builds may drop the DB on a schema change; release builds need a real migration. `calibrationVersion` stays informational (the newest calibration a row was measured under), not a key: it can repeat only if the calibration DataStore is lost while the DB survives, and nothing joins on it. | Spec §16 caps the loss at one flush interval. Measured on the API 34 emulator (Settings, `input swipe`): after 12 s the DB equals the logcat sum of counted events (242.026 vs 242.027 mm, display rounding); `kill -9` right after scrolling lost exactly the unflushed ~4 s (463.85 mm), the system restarted the service by itself and the next flush added up (704.19 mm = 242.03 + 462.16). **`am force-stop` also clears the service from `enabled_accessibility_services` on API 34** — measurement stays off until the user turns it on again, and Home says so (spec §32). | accepted |
| ADR-027 | 2026-09-24 | **Nothing leaves the phone through Android's data transfer.** Besides `allowBackup="false"` (API 28–30), `android:dataExtractionRules` excludes every domain from both `<cloud-backup>` and `<device-transfer>` (API 31+): the database, both DataStores and any file stay on the phone that measured them. Taking data along = CSV export (Phase 6). Guards: `PolicyGuardTest` pins the rules file; `check_manifest_policy.py` requires the attribute, checks `uses-permission-sdk-23` as well, matches the androidx signature permission against the manifest's own package exactly, and fails on any exported component other than the launcher activity that has no permission. The service and the usage sync read settings through a flow that does **not** fall back to defaults on a read error — an unreadable file keeps the exclusions applied last instead of measuring apps the user excluded. | Security review of Phase 3: on API 31+ `allowBackup="false"` stops cloud backup but, on some devices, not device-to-device transfer, which would copy the scroll history, time in app and the card calibration to a new phone — against the disclosure's "data zůstávají v telefonu" and the stale-calibration risk ADR-024 names. The history is not worth weakening that promise; the open point on D2D transfer (handoff.md) is closed by this. | accepted |
